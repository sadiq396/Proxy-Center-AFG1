# Proxy Center AFG

پروژه یکپارچه مینی‌اپ تلگرام و پنل ابزارها با رابط فارسی و پوسته تیره. رابط مینی‌اپ در مسیر `/` اجرا می‌شود و رابط قدیمی دیپلوی سنایی نیز در مسیر `/sanaei` نگه داشته شده است.

## محتویات

- رابط واکنش‌گرا برای موبایل، صفحه اصلی، کانفیگ‌ها، پروکسی تلگرام، دانلودها، پروفایل، راهنمای فارسی، چت و پشتیبانی.
- اعتبارسنجی `Telegram.WebApp.initData` سمت سرور با امضای HMAC. شناسه مدیر فقط در بک‌اند بررسی می‌شود.
- ربات تلگرام سبک با `/start` و دکمه بازکردن مینی‌اپ؛ اشتراک شماره تلفن کاملاً اختیاری و با دکمه درخواست تماس تلگرام است. شماره به‌طور خودکار از پروفایل دریافت نمی‌شود.
- مدیریت کاربران، مسدود/رفع مسدودسازی، پاسخ تیکت پشتیبانی، اعلان‌ها، پیام همگانی داخل مینی‌اپ و ثبت رویدادهای مدیریتی.
- گردآوری بهترین تلاش از دو مخزن عمومی GitHub و کانال‌های عمومی تلگرام، حذف موارد تکراری و پینگ ICMP واقعی از سرور میزبان (اگر ابزار و دسترسی ICMP در هاست فراهم باشد).
- کد قدیمی دیپلوی سنایی حفظ شده، اما رابط ساخت پنل به‌صورت پیش‌فرض مخفی است؛ مسیر `/sanaei` فقط با `ENABLE_SANAEI_UI=true` فعال می‌شود.
- Dockerfile و `railway.json` برای استقرار روی میزبان‌های سازگار با Node.js/Docker.

## راه‌اندازی محلی

1. Node.js نسخه 20 یا بالاتر نصب باشد.
2. `npm install` اجرا شود.
3. `.env.example` را به `.env` کپی کنید و مقادیر خود را تنظیم کنید. `.env` را به GitHub آپلود نکنید.
4. `BOT_TOKEN` را با توکن فعال ربات آزمایشی خود در تنظیمات امن سرویس جایگزین کنید. توکن ثابت داخل کد عمداً باطل شده و کار نمی‌کند.
5. `WEBAPP_URL` را با آدرس HTTPS واقعی سرویس تنظیم کنید.
6. `BOT_POLLING_ENABLED=true` را فقط روی یک نمونه اجرا قرار دهید. اگر پروژه هم‌زمان روی دو سرویس فعال است، در یکی از آن‌ها `false` بگذارید تا دو poller برای یک ربات با هم تداخل نکنند.
7. `npm start` اجرا شود.

برای پیش‌نمایش محلی API بدون تلگرام، فقط در محیط محلی مقدارهای زیر را تنظیم کنید: `NODE_ENV=development` و `ALLOW_DEMO_LOGIN=true`. سپس صفحه را با `?demo=1` باز کنید. برای نمایش پنل مدیر آزمایشی، از `?demo=admin` استفاده کنید. **هرگز حالت demo را در محیط production فعال نکنید.** سرور در حالت production این روش ورود را قبول نمی‌کند.

## استقرار از GitHub

### Railway

1. کل پوشه پروژه را در یک repository شخصی GitHub قرار دهید.
2. در Railway یک سرویس از همان repository بسازید. Dockerfile به‌صورت خودکار استفاده می‌شود.
3. در Variables، مقدارهای `BOT_TOKEN`، `WEBAPP_URL`، `ADMIN_ID=6891242026`، `SUPPORT_USERNAME=sadiq_AFG1`، `PROVIDER_FANCY`، `PROVIDER_NAME` و `BOT_POLLING_ENABLED=true` را وارد کنید.
4. دامنه HTTPS تولید کنید، مقدار دقیق آن را در `WEBAPP_URL` ثبت کنید و سرویس را redeploy کنید.
5. در BotFather آدرس وب‌اپ را برای ربات تنظیم کنید یا از دکمه `/start` و دکمه منوی ربات استفاده کنید. ربات از متغیر محیطی آدرس وب‌اپ را برای تنظیم دکمه منو می‌خواند.

### VibeNest یا میزبان Node/Docker دیگر

همان repository را انتخاب و به‌عنوان برنامه Node.js/Docker اجرا کنید. برنامه به `process.env.PORT` گوش می‌دهد. متغیرهای محیطی مشابه Railway هستند. سازگاری واقعی به امکان اجرای Docker/Node، دسترسی شبکه خروجی، سیاست ذخیره‌سازی و محدودیت‌های پلن سرویس بستگی دارد؛ وجود فضای دیسک به معنی RAM بیشتر نیست.

**اگر یک ربات را هم‌زمان روی هر دو سرویس اجرا می‌کنید:** فقط یکی را با `BOT_POLLING_ENABLED=true` اجرا کنید؛ دیگری را روی `false` بگذارید. برای اینکه چت، کاربران و تیکت‌ها در دو نصب مستقل مشترک باشند، هر دو باید به یک پایگاه داده مشترک وصل شوند. نسخه فعلی از فایل `data/store.json` استفاده می‌کند و این فایل فقط روی همان نمونه مشترک است.

## تنظیمات اصلی

| متغیر | توضیح |
|---|---|
| `BOT_TOKEN` | توکن فعال ربات. مقدار ثابت موجود در src/config.js باطل شده است؛ توکن فعال را فقط در Variables/Secrets قرار دهید. هرگز توکن فعال را در HTML یا مخزن عمومی نگذارید. |
| `WEBAPP_URL` | آدرس عمومی HTTPS مینی‌اپ. |
| `ADMIN_ID` | شناسه عددی مدیر اصلی؛ مقدار پیش‌فرض `6891242026`. |
| `SUPPORT_USERNAME` | نام کاربری پشتیبانی بدون `@`. |
| `PROVIDER_FANCY` | نام استایل‌دار ارائه‌دهنده در پایین صفحه. |
| `PROVIDER_NAME` | نام نمایشی ارائه‌دهنده. |
| `BOT_POLLING_ENABLED` | فعال‌سازی دریافت پیام ربات؛ فقط روی یک نمونه `true`. |
| `DATA_DIR` | مسیر فایل داده؛ برای ذخیره ماندگار، volume پایدار لازم است. |
| `PORT` | توسط میزبان تنظیم می‌شود یا محلی `3000`. |

## APIهای اصلی

- `GET /health` وضعیت زنده برنامه
- `GET /api/public-config` تنظیمات عمومی رابط
- `GET /api/me` پروفایل تأییدشده تلگرام
- `GET /api/configs?type=v2ray&limit=10&protocol=all` کانفیگ‌های عمومی و تست TCP
- `GET /api/configs?type=telegram&limit=10` پروکسی‌های تلگرام
- `GET/POST /api/chat`، `POST /api/chat/presence` برای heartbeat آنلاین‌ها و `PUT/DELETE /api/chat/:id` چت
- `GET/POST /api/support` و مسیرهای پاسخ به تیکت
- `/api/admin/*` مدیریت سمت سرور، فقط برای شناسه `ADMIN_ID`
- `/sanaei` و APIهای قدیمی سنایی فقط اگر `ENABLE_SANAEI_UI=true` باشد؛ APIهای قدیمی مربوط به استقرار، فورک و وضعیت آن نیز در حالت پیش‌فرض پاسخ 404 می‌دهند

## ملاحظات مهم پیش از تولید

- توکن قبلی که کاربر اعلام کرده باطل شده بود و عمداً داخل فایل‌ها کپی نشده است؛ نمونه `.env.example` فقط placeholder دارد.
- `data/store.json` پایگاه‌داده سبک فایل‌محور است. اگر میزبان فایل سیستم ماندگار نداشته باشد، داده‌ها بعد از redeploy ممکن است از بین بروند؛ برای استفاده جدی، volume پایدار یا پایگاه‌داده مشترک لازم است.
- شماره تلفن فقط پس از فشردن دکمه اختیاری «اشتراک شماره» در ربات دریافت می‌شود. کاربر می‌تواند بعداً از صفحه پروفایل شماره را حذف کند؛ تلگرام شماره را خودکار از `initData` تحویل نمی‌دهد.
- تست پروکسی به شکل TCP connect و از محل سرور میزبان است. این معیار معادل پینگ از گوشی یا تأیید کامل کارکرد پروتکل/تونل نیست. نتایج ممکن است کمتر از تعداد انتخابی باشند.
- منابع GitHub و پیش‌نمایش عمومی کانال‌های تلگرام ممکن است تغییر کنند، rate-limit شوند یا در بعضی میزبان‌ها قابل‌دسترسی نباشند. در چنین وضعی خطا/کمبود نتایج گزارش می‌شود؛ وضعیت جعلی ساخته نمی‌شود.
- ساخت یا اجرای Sanaei/Xray به منابع و قابلیت‌های سیستمی نیاز دارد که همه میزبان‌های اپلیکیشن رایگان فراهم نمی‌کنند. اتوماسیون Marzban در این ZIP پیاده‌سازی نشده و نباید از صفحه راهنما به‌عنوان قابلیتی آماده برداشت شود. صفحه `/sanaei` باقی مانده، اما هر استقرار پنل باید جداگانه در محیط واقعی تست شود.
- قبل از بازکردن دسترسی عمومی، یک تست انتها‌به‌انتها انجام دهید: `/health`، `/start` ربات، ورود از داخل تلگرام، احراز هویت مدیر، کپی کانفیگ، چت، پشتیبانی، بلاک و ماندگاری داده.
